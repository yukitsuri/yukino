# 16. Тестирование и тест-раннер

Yukino предоставляет первоклассную встроенную систему модульного и интеграционного тестирования. Компилятор и рантайм языка включают в себя встроенный тестовый раннер с параллельным исполнением, изоляцией воркеров в отдельных процессах, защитой от зависаний (watchdog таймауты), удобной фильтрацией и лаконичным цветным выводом.

## 1. Быстрый старт: команда yukino test

Для запуска всех тестов в текущем проекте выполните команду:

```sh
yukino test
```

Раннер выполнит следующие шаги:
1. Автоматически активирует режим сборки тестов (`cfg(test)`).
2. Соберет модули проекта и интеграционные тесты из директории `tests/`.
3. Подготовит исполняемый тестовый бинарник с входной точкой раннера.
4. Запустит тесты в изолированных процессах-воркерах, отображая статус в реальном времени.
5. Выведет сводную информативную таблицу результатов и подробности ошибок, если они возникли.

## 2. Структура тестов в проекте

### 2.1 Модульные (unit) тесты внутри src/

Модульные тесты размещаются прямо в файлах исходного кода в директории `src/` рядом с тестируемым кодом или во вспомогательных модулях, защищенных атрибутом `#[cfg(test)]`:

```yukino
// src/math.ykn
public fun add(a: int32, b: int32): int32 {
    a + b
}

#[test]
fun test_add() {
    assert(add(2, 2) == 4)
}
```

При сборке в обычном режиме (`yukino build`) функции с атрибутом `#[test]` автоматически удаляются компилятором (dead code elimination) и не попадают в итоговый бинарник приложения или библиотеки.

### 2.2 Интеграционные тесты в директории tests/

Интеграционные тесты размещаются в отдельной директории `tests/` в корне проекта (или директории, указанной в `tests_dir` в манифесте). Каждый `.ykn` файл в этой директории рассматривается как отдельный набор тестов:

```
my_project/
├── yuki.toml
├── src/
│   ├── lib.ykn
│   └── calc.ykn
└── tests/
    └── integration.ykn
```

Внутри интеграционных тестов можно подключать модули текущего проекта по имени пакета:

```yukino
// tests/integration.ykn
load my_project.calc: evaluate

#[test]
fun test_end_to_end_calculation() {
    set result = evaluate("2 + 2 * 2")
    assert(result == 6)
}
```

Тесты группируются по сьютам (suite) согласно имени файла или модуля: тесты из `src/main.ykn` отображаются в сьюте `main`, тесты из `tests/integration.ykn` — в сьюте `tests` или `integration`.

## 3. Условная компиляция: cfg(test) и cfg!(test)

Для кода, который должен компилироваться исключительно при тестировании (например, вспомогательные моки, генераторы данных или расширенные проверки), используйте предикат `test`:

### Атрибут #[cfg(test)]
```yukino
#[cfg(test)]
struct TestMock {
    data: string
}

#[cfg(test)]
fun create_mock_client(): TestMock {
    TestMock { data: "mock payload" }
}
```

### Встроенный макрос cfg!(test)
```yukino
fun initialize_service() {
    if cfg!(test) {
        // Логика быстрого мока для тестов
    } else {
        // Реальное подключение к внешнему серверу
    }
}
```

## 4. Атрибуты тестов

### 4.1 #[test]

Помечает функцию как тест. Тестовая функция не должна принимать аргументов и не должна возвращать значений:

```yukino
#[test]
fun test_basic_equality() {
    set x = 10
    set y = 20
    assert(x + y == 30)
}
```

### 4.2 #[should_panic]

Указывает, что тест считается успешно пройденным **только** в том случае, если функция завершилась с вызовом `panic`:

```yukino
struct ValidationError {
    message: string
}

#[test]
#[should_panic]
fun test_must_fail() {
    panic(ValidationError { message: "invalid input" })
}
```

Также поддерживается сопоставление подстроки сообщения об ошибке:

```yukino
#[test]
#[should_panic = "division by zero"]
fun test_zero_div() {
    panic(ValidationError { message: "critical: division by zero detected" })
}
```

Если паника не произошла или текст ошибки не содержит указанной подстроки, тест завершается со статусом `FAIL`.

### 4.3 #[ignore]

Позволяет временно исключить медленный, ресурсоемкий или внешний тест из стандартного прогона:

```yukino
#[test]
#[ignore]
fun test_long_running_migration() {
    // Не запускается при обычном yukino test
}

#[test]
#[ignore = "Требуется доступ к внешнему серверу"]
fun test_remote_api() {
    // Пояснение причины пропуска
}
```

Компилятор выдает предупреждение `W0423` при наличии пропущенных тестов. Для запуска пропущенных тестов используйте флаги `--ignored` или `--include-ignored`.

### 4.4 #[timeout_ms]

Задает индивидуальный лимит времени выполнения тестовой функции в миллисекундах. Если время выполнения теста превысит указанное значение, рабочий процесс будет принудительно остановлен сторожевым таймером (watchdog), а тест будет помечен как сбойный с подробным сообщением:

```yukino
#[test]
#[timeout_ms = 500]
fun test_responsive_operation() {
    // Должно завершиться быстрее, чем за 500 мс
}
```

## 5. Командная строка: флаги yukino test

Команда `yukino test` поддерживает набор флагов для точечного управления прогоном тестов:

| Флаг | Описание |
| :--- | :--- |
| `<FILTER>` | Запуск тестов, имя которых содержит указанную подстроку (например, `yukino test math`) |
| `--exact` | Точное совпадение имени теста с фильтром |
| `--nocapture` | Вывод в консоль потоков stdout и stderr тестов во время их исполнения |
| `-j, --threads <N>` | Количество параллельных потоков тестирования |
| `--ignored` | Запуск **только** пропущенных тестов с атрибутом `#[ignore]` |
| `--include-ignored` | Запуск всех тестов, включая тесты с `#[ignore]` |
| `--fail-fast` | Немедленная остановка тестирования после первого упавшего теста |
| `--list` | Печать списка доступных тестов без их фактического запуска |
| `-q, --quiet` | Лаконичный режим с минимальным выводом |
| `--timeout <MS>` | Переопределение таймаута по умолчанию для всех тестов (в мс) |
| `-b, --rebuild` | Принудительная полная пересборка тестового бинарника |
| `-p, --package <NAME>` | Запуск тестов конкретного пакета в воркспейсе |
| `-F, --features <LIST>` | Активация фичей через запятую |
| `--all-features` | Включение всех доступных фичей |
| `--no-default-features` | Отключение фичей по умолчанию |

### Примеры вызова

```sh
# Запустить тесты, содержащие в названии "crypto"
yukino test crypto

# Запустить конкретный тест с точным совпадением
yukino test "math::test_add" --exact

# Вывести логи stdout из тестов напрямую в терминал
yukino test --nocapture

# Запустить в 4 потока и остановиться при первой ошибке
yukino test -j 4 --fail-fast

# Просмотреть список всех тестов
yukino test --list
```

## 6. Конфигурация в yuki.toml

Поведение тестового раннера по умолчанию можно настроить в манифесте проекта `yuki.toml` в секции `[test]`:

```toml
[test]
# Количество параллельных потоков ("auto" или фиксированное число)
threads = 4

# Глобальный таймаут на тест по умолчанию (в миллисекундах)
timeout_ms = 30000

# Перехватывать вывод тестов (true) или выводить сразу (false)
capture_output = true

# Автоматически останавливаться при первой ошибке
fail_fast = false

# Директория с интеграционными тестами (по умолчанию "tests")
tests_dir = "tests"
```

## 7. Интерфейс вывода результатов

Во время выполнения тестов раннер динамически отображает текущий прогресс на одной строке:
- Анимированный спиннер активного воркера.
- Квалифицированное имя теста с цветовой подсветкой разделителя `::`.
- Наглядный прогресс-бар вида `[###       ]`.
- Счетчик выполненных тестов вида `[14/42]` и прошедшее время.

После завершения всех тестов выводится лаконичная сводная таблица без лишнего визуального шума:

```
SUITE          TESTS     STATUS     TIME    
main           3/3       [OKIE]     154ms   
tests          1/1       [OKIE]     2ms     

Result: OKIE | 4 passed, 0 failed, 0 skipped in 0.08s
```

Статусы сьютов:
- `[OKIE]` — все тесты в наборе успешно пройдены.
- `[FAIL]` — один или более тестов завершились ошибкой.
- `[SKIP]` — все тесты в наборе были пропущены (`#[ignore]`).

В случае обнаружения ошибок под таблицей выводится блок с подробным диагностическим отчетом: точное имя упавшего теста, перехваченный стек или сообщение паники, а также статус таймаута при превышении лимита времени.
