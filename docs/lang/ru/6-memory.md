# Модель памяти, владение и регионы

Yukino предлагает детерминированную модель управления памятью: **производительность на уровне Си и Rust без накладных расходов сборщика мусора (GC)** и **статические гарантии отсутствия висячих указателей и утечек памяти**.

В этой главе описывается архитектура управления памятью Yukino: жизненный цикл ресурсов, аффинная система типов, правила статического верификатора заимствований (Borrow Checker) и региональные bump-аллокаторы.

## 1. Фундамент: почему в Yukino нет Garbage Collector и malloc/free

В существующих языках программирования исторически сложилось два подхода:

1. **Ручное управление памятью (Си, C++):**  
   Вызовы `malloc()` и `free()` возлагаются на программиста. Ошибки приводят к утечкам памяти, повторному освобождению (Double-Free) или разыменованию освобожденных указателей (Use-After-Free), что влечет аварийное завершение (`SIGSEGV`) или уязвимости безопасности.
2. **Сборщик мусора (Java, Go, C#, Python, JavaScript):**  
   Фоновый рантайм-поток сканирует граф объектов кучи. Это влечет за собой увеличение потребления памяти метаданными и паузы выполнения (Stop-The-World).

### Подход Yukino

Yukino решает задачу детерминированно: **полная безопасность без накладных расходов сборщика мусора**.  
Компилятор статически анализирует жизненные циклы переменных, точки владения и границы заимствования, генерируя код с освобождением памяти в момент выхода из соответствующей области видимости или региона.

Ключевая деталь этой модели: фигурные скобки `{}` играют двойную роль. Они одновременно задают область видимости переменных и являются областью выделения памяти (регионом). Когда выполнение программы покидает блок, весь регион очищается одним действием: все аллоцированные в нем данные — строки, срезы, экземпляры классов — освобождаются вместе, независимо от того, где именно внутри блока они были созданы.

## 2. Архитектура управления памятью: владение и заимствование

Модель памяти Yukino опирается на следующие фундаментальные принципы:

- **Аффинная система типов (Affine Ownership):**  
  Каждое значение нетривиального типа имеет ровно одну переменную-владельца. Владелец определяет время жизни и точку освобождения ресурса.
- **Семантика перемещения (Move Semantics):**  
  При присваивании значения переменной или передаче его в вызов функции владение передается новому контексту. Предыдущая переменная статически инвалидируется в точке перемещения, исключая повторное использование или множественное освобождение.
- **Разделяемое заимствование (`ref T`):**  
  Передача указателя на область памяти только для чтения без передачи прав владения. Допускается произвольное количество параллельных неизменяемых заимствований.
- **Эксклюзивное заимствование (`ref ~T`):**  
  Передача указателя для модификации по месту (in-place mutation). В каждый момент времени для конкретного ресурса разрешена либо единственная изменяемая ссылка, либо произвольное число неизменяемых ссылок (**инвариант Aliasing XOR Mutability**).

## 3. Как устроены обычные строки (string) в памяти

Строки — самый наглядный пример модели памяти в действии.

### Дескриптор строки (Fat Pointer)

В Yukino строка `string` — это не массив байтов сам по себе, а компактный **дескриптор** размером всего 16 байт на 64-битной системе:

```text
Строка: { ptr: указатель на байты, len: длина в байтах }
```

```yukino
set greeting = "Привет, мир!"
```

- Сам текст `"Привет, мир!"` лежит в памяти как последовательность байт.
- Переменная `greeting` на стеке хранит только `{ ptr, len }`.
- Строки в Yukino **неизменяемы (immutable)**. Никакая операция не может испортить байты существующей строки.

### Что происходит при присваивании `set s2 = s1`?

Строка — это **Copy-тип**, поэтому присваивание копирует её 16-байтный дескриптор:

```yukino
set s1 = "Yukino"
set s2 = s1 // копирование 16 байт дескриптора: обе переменные s1 и s2 валидны
println(s1) // "Yukino"
println(s2) // "Yukino"
```

На машинном уровне копируются только 16 байт дескриптора `{ ptr, len }` (значения регистров CPU): второй буфер байтов не создается, и `s2` указывает на те же байты в памяти. В ранних версиях Yukino строка считалась аффинным типом, из-за чего исходная переменная `s1` сгорала (`use of moved value`), вынуждая везде писать `ref s`. Это ограничение было снято: так как строки строго неизменяемы, дескриптор свободно копируется, обе переменные остаются валидными, а для их чтения указывать `ref` не требуется.

### А если мы конкатенируем строки (`s1 + s2`)?

```yukino
set a = "Hello, "
set b = "Yukino!"
set c = a + b // Выделяется новый буфер памяти под "Hello, Yukino!"
```

Оператор `+` аллоцирует новый непрерывный участок памяти в **текущем регионе** и копирует туда байты обеих строк. Дескриптор `c` указывает на этот новый буфер.

### Как принудительно сделать полную независимую копию?

Строки в Yukino неизменяемы, поэтому для них глубокое копирование не требуется: метод `.cp()` для строки возвращает ее дескриптор без повторного выделения памяти. Глубокое копирование актуально для изменяемых буферов — срезов `T[]` и `bytes`, где `.cp()` выделяет новый буфер в текущем регионе и копирует элементы:

```yukino
set original: uint8[] = [1, 2, 3]
set clone = original.cp() // физически выделяет новый независимый буфер
```

## 4. Аффинное владение и перемещение (Ownership & Move)

### 4.1 Copy-типы и Affine-типы

Все типы данных разделены на две группы:

1. **Copy-типы (скаляры, тривиальные агрегаты и строки):**  
   Числа (`int8`..`int64`, `uint8`..`uint64`, `float32`, `float64`), булевы флаги (`bool`), символы (`char`), строки `string`, указатели `ptr`, типы функций, `null`, а также кортежи и union-типы, целиком состоящие из Copy-типов. Неизменяемая ссылка (`ref T`) также копируется.  
   Они дешево и автоматически копируются побитово при любом присваивании или передаче в функцию:
   ```yukino
   set a: int32 = 42
   set b = a // b = 42, переменная 'a' по-прежнему валидна

   set s1 = "текст"
   set s2 = s1 // дескриптор скопирован, обе переменные валидны
   ```
2. **Affine-типы (типы с ресурсами и изменяемыми объектами):**  
   Байты `bytes`, массивы `T[]`, карты `map`, структуры `struct`, классы `class`, интерфейсы, перечисления `enum`. Каждое такое значение имеет **ровно одного владельца**.

### 4.2 Перемещение владения (move)

Когда значение аффинного типа передается в другую переменную или как аргумент функции по значению, владение **перемещается (move)**:

```yukino
struct DatabaseConnection {
    host: string
    port: int32
}

fun close_connection(conn: DatabaseConnection) {
    // conn теперь принадлежит этой функции и будет уничтожен при выходе
}

set my_conn = DatabaseConnection { host: "localhost", port: 5432 }

// Передаем владение в функцию:
close_connection(my_conn)

// ОШИБКА КОМПИЛЯЦИИ: my_conn больше не существует в этом скоупе!
// print(my_conn.host)
```

### 4.3 Защита от использования после перемещения (Use-After-Move)

В других языках обращение к перемещенному объекту может привести к чтению мусора или падению в рантайме. В Yukino компилятор отслеживает это на этапе статического анализа:

```yukino
struct Packet {
    payload: string
}

set p1 = Packet { payload: "secret data" }
set p2 = p1 // Право собственности перемещено в p2

// Ошибка компиляции E0501: use of moved value 'p1'
// set data = p1.payload
```

## 5. Заимствование (Borrowing): Ссылки vs Владение

Что делать, если мы хотим передать структуру или данные в функцию для вычислений или проверки, **но не хотим отдавать владение**?  
Для этого используются **ссылки (заимствование / borrowing)**.

### 5.1 Техническое сопоставление семантик

| Критерий | Семантика владения (`T`) | Семантика заимствования (`ref T` / `ref ~T`) |
| :--- | :--- | :--- |
| **Управление временем жизни** | Исключительное право на инициализацию и уничтожение ресурса | Время жизни строго ограничено контекстом владельца |
| **Передача аргументов** | Семантика перемещения (Move) либо побитовая копия (Copy) | Передача указателя без смены и инвалидации владельца |
| **Память на машинном уровне** | Размещение на стеке или дескриптор в локальном регионе | Прямой 64-битный указатель на память объекта |
| **Инвариант доступа** | Единственный владелец | Множество читателей (`ref`) XOR один писатель (`ref ~`) |

### 5.2 Неизменяемые ссылки (ref T): разделяемый доступ на чтение

Неизменяемая ссылка позволяет обращаться к полям структуры или байтам строки, гарантируя, что вызываемый код не сможет мутировать целевой буфер.

В Yukino ссылка указывается ключевым словом `ref` как при объявлении параметра функции, так и **явно в месте вызова**:

```yukino
struct UserProfile {
    name: string
    age: int32
}

// Функция принимает ссылку только для чтения:
fun print_user(ref u: UserProfile) {
    println("Пользователь: ${u.name}, возраст: ${u.age}")
    // rewrite u = ... -- ОШИБКА КОМПИЛЯЦИИ (E0503): нельзя переприсваивать переменную, принятую по неизменяемой ссылке!
}

set user = UserProfile { name: "Алиса", age: 25 }

// Явно передаем по ссылке через ref:
print_user(ref user)

// 'user' остался у нас! Мы можем продолжать им пользоваться:
println("Имя владельца: ${user.name}")
```

#### Заимствование обычных строк:

#### Когда нужен и когда не нужен ref для чтения:

Поскольку строки `string` являются Copy-типами, их не требуется передавать по ссылке `ref`: передача по значению `compute_stats(title)` копирует только 16 байт дескриптора и оставляет переменную у вызывающего полностью валидной:

```yukino
fun compute_stats(s: string) -> int64 {
    return s.len()
}

set title = "Юкино Юкиношита > fiction"
set length = compute_stats(title)
// title не был перемещен и полностью доступен
```

Неизменяемая ссылка `ref T` в Yukino используется в первую очередь для **тяжёлых структур (`struct`)**, размер которых в памяти составляет десятки или сотни байт (чтобы не копировать все поля структуры на стек), а также для работы со срезами и интерфейсами:

```yukino
struct LargeData {
    matrix: float64[16]
    label: string
}

fun process_data(ref d: LargeData) {
    // передается 8-байтный указатель вместо копирования 144 байт структуры
}
```

### 5.3 Изменяемые ссылки (ref ~T): один эксклюзивный писатель

Если функция должна модифицировать поля существующей структуры или переприсвоить значение переменной владельца на месте (in-place), используется изменяемая ссылка `ref ~`:

```yukino
struct Counter {
    value: int64
}

// Принимает изменяемую ссылку:
fun increment(ref ~c: Counter, delta: int64) {
    rewrite c.value = c.value + delta
}

set my_counter = Counter { value: 10 }

// Явно передаем право на мутацию через ref ~:
increment(ref ~my_counter, 5)

println("Новое значение: ${my_counter.value}") // 15
```

#### Мутация строковой переменной по ссылке:
Так как сам буфер строки в памяти неизменяем, функция может обновить строковую переменную вызывающего только перезаписав её 16-байтный дескриптор. Для этого используется `ref ~s: string`:

```yukino
fun append_suffix(ref ~s: string, suffix: string) {
    rewrite s = s + suffix
}

set message = "Обработка"
append_suffix(ref ~message, " завершена.")
println(message) // "Обработка завершена."
```

### 5.4 Железное правило Borrow Checker

Чтобы предотвратить гонки данных (data race), чтение неконсистентных данных и повреждение памяти, компилятор Yukino применяет фундаментальное правило эксклюзивности:

> **В любой точке программы для одного значения допустимо либо:**  
> - **Сколько угодно неизменяемых читателей (`ref T`)**  
> **ЛИБО**  
> - **Ровно один эксклюзивный писатель (`ref ~T`)**  
> *(Но никогда читатели и писатель одновременно!)*

### 5.5 Как писать оптимизированный по памяти код (Практические правила)

1. **Скаляры и строки (`int32`, `bool`, `string`) передавайте по значению.**  
   Передача 1–16 байт напрямую в регистрах процессора происходит быстрее, чем передача адреса в памяти и последующее разыменование указателя.
2. **Тяжёлые структуры (`struct`) передавайте по ссылке `ref T`.**  
   Для структур размером более 16 байт передача по ссылке `ref` передаёт ровно один 64-битный указатель и не тратит время на копирование всех полей на стек.
3. **Модифицируйте данные на месте через `ref ~T`.**  
   Изменение существующего объекта или перезапись переменной через `ref ~` избавляет от необходимости создавать промежуточные структуры и возвращать кортежи наружу.
4. **Оборачивайте циклы в блоки `region { ... }`.**  
   Если внутри цикла создаются временные строки или массивы, блок `region` сбрасывает указатель арены памяти в конце каждой итерации за $O(1)$. Потребление ОЗУ остаётся плоским независимо от числа итераций.
5. **Для побайтовой сборки используйте `bytes`, а не сотни конкатенаций `+`.**  
   Многократная склейка строк через `+` выделяет новый буфер на каждом шаге. Если нужно собрать сложный документ или бинарный пакет, используйте мутабельный буфер `bytes` с методом `.push()` или `reserve()`.

## 6. Региональная модель памяти (Regions)

Большинство языков выделяют память под каждую динамическую строку или массив отдельным обращением к системному аллокатору (`malloc`). Это приводит к фрагментации памяти и просадкам производительности.

В Yukino память динамических объектов управляется **регионами (arena/region allocators)**.

### 6.1 Bump-аллокация и мгновенное освобождение за O(1)

Внутри региона выделение памяти выполняется через bump-аллокатор (линейное выделение в непрерывном буфере): указатель смещения инкрементируется на размер запрашиваемой структуры данных с учетом требований к машинному выравниванию (alignment):

```text
[ Регион: Непрерывный буфер арены ]
[ Объект 1 ][ Строка 2 ][ Массив 3 ][ Свободно ...  ] -> Указатель вершины сдвигается за 1 такт CPU
```

Когда область видимости региона завершается, рантайм сбрасывает указатель арены до исходной отметки за $O(1)$ без поэлементного вызова деструкторов.

### 6.2 Неявные регионы функций и кадры стека

Каждая функция в Yukino автоматически получает свой региональный фрейм. Все временные строки, конкатенации и промежуточные массивы внутри функции живут в ее локальном регионе.

Когда функция завершает выполнение, вся временная память мгновенно очищается:

```yukino
fun format_report(id: int32) -> string {
    // Временные строки создаются в локальном регионе функции
    set prefix = "Отчет №"
    set num_str = cast(id, "string")
    set full = prefix + num_str

    // Возвращаемое значение full безопасно передается в регион вызывающего кода!
    return full
}
```

### 6.3 Сброс памяти в циклах (region в теле цикла)

В других языках циклы, создающие строки или массивы на каждой итерации, часто приводят к утечкам памяти или перегрузке сборщика мусора.

Регионные метки (`save_mark` / `restore_mark`) ставятся явными блоками `region { ... }`: при входе в блок запоминается текущая отметка арены, при выходе указатель сбрасывается к ней за O(1). Если такой блок поместить в тело цикла, память каждой итерации будет освобождаться сразу по завершении шага:

```yukino
fun process_many_items() {
    set i = 0
    while i < 1_000_000 {
        region {
            // На каждой итерации создается новая временная строка:
            set temp = "Элемент №" + cast(i, "string")
            do_light_work(temp)
        }
        rewrite i = i + 1
        // temp и все промежуточные строки итерации уже МГНОВЕННО очищены!
        // Расход памяти НЕ РАСТЕТ независимо от количества итераций!
    }
}
```

Обычные циклы `for`, `while` и `loop` без явного блока `region` меток не ставят: временные значения, созданные в итерациях, живут в локальном регионе функции до ее завершения.

### 6.4 Явные блоки region { ... } для тяжелых задач

Если вам нужно выполнить тяжелую промежуточную работу (например, распарсить JSON на 50 мегабайт или обработать большой пакет строк) и освободить всю память **немедленно**, используется явный блок `region`:

```yukino
fun handle_batch(records: string[]) {
    // Обрабатываем тяжелый блок данных:
    region {
        set buffer: string[] = []
        for i in 0..records.len() {
            buffer.push(records[i] + " [validated]")
        }
        send_to_network(buffer)
    }
    // В этой точке указатель арены региона сбрасывается до метки входа,
    // мгновенно возвращая всю память буфера buffer и временных строк в пул за O(1).

    continue_other_work()
}
```

### 6.5 Escape-анализ: запрет побега ссылок

Компилятор статически проверяет, чтобы ссылка на объект, живущий в локальном регионе, не могла быть сохранена в более долгоживущий контекст:


## 7. Отложенное выполнение: defer

Для гарантированного освобождения системных ресурсов (дескрипторов файлов, мьютексов, сокетов) используется конструкция `defer`:

```yukino
fun read_config_file(path: string) -> string {
    set file = open_file(path)
    // Гарантируем закрытие файла при любом исходе:
    defer {
        close_file(file)
    }

    if file.is_empty() {
        return "" // defer сработает здесь перед выходом
    }

    set content = file.read_all()
    return content // и здесь defer тоже гарантированно сработает!
}
```

- Инструкции `defer` выполняются в порядке, обратном объявлению (**LIFO** — Last In, First Out).
- `defer` срабатывает при обычном возврате (`return`), преждевременном прерывании (`break`, `continue`), а также при аварийной раскрутке стека через исключения (`sus`/`catch`/`finally`).

## 8. Шпаргалка: что выбирать на практике

| Ситуация | Что использовать | Пример сигнатуры |
| :--- | :--- | :--- |
| Нужно передать простое число, флаг, байт или строку | Обычный скаляр / строка по значению (Copy) | `fun calc(x: int32, s: string)` |
| Нужно просто прочитать поля структуры без копирования | Неизменяемая ссылка `ref` | `fun inspect(ref user: User)` |
| Нужно обновить/изменить существующий объект на месте | Изменяемая ссылка `ref ~` | `fun update(ref ~user: User, ref ~buf: bytes)` |
| Функция должна забрать объект и стать его единственным хозяином | Передача владения `T` (Move) | `fun register_connection(conn: Connection)` |
| Внутри функции в цикле создается много временных строк | Блок `region { ... }` в теле цикла | `for i in 0..list.len() { region { set s = list[i] + "\n" } }` |
| Большой блок промежуточных аллокаций, память которого нужна прямо сейчас | Блок `region { ... }` | `region { set big_tree = build_tree() }` |
| Нужно закрыть файл, освободить сокет или отпустить лок | `defer { ... }` | `defer { unlock(mutex) }` |
