# Тулчейн и структура проекта

CLI-менеджер проектов `yukino` управляет жизненным циклом приложений и библиотек: инициализирует шаблоны, управляет манифестом `yuki.toml`, разрешает локальные, Git и архивные зависимости, отслеживает блокировки в `yuki.lock`, компилирует скрипты предсборки `build.ykn` и координирует низкоуровневый компилятор `yukic`.

## 1. Команды yukino CLI

Утилита `yukino` доступна глобально в системе и принимает подкоманды и флаги.

### 1.1 Создание проекта: yukino new

Создает новый проект с базовым скелетом:

```sh
# Исполняемый бинарник (по умолчанию, генерирует src/main.ykn и секцию [bin] в yuki.toml)
yukino new my_app

# Статическая библиотека (генерирует <имя>/lib.ykn и секцию [lib] с output = "static" в lib.toml)
yukino new my_lib --static

# Динамическая / C-совместимая библиотека (.so / .dll, output = "shared" в lib.toml)
yukino new my_shared --dynamic

# Пакет процедурного макроса (генерирует <имя>/lib.ykn и output = "macro" в lib.toml)
yukino new my_macro --macro

# Универсальный воркспейс (генерирует yukispace.toml, каталоги libs/ и apps/)
yukino new my_workspace --workspace

# Инициализация проекта в текущем каталоге (существующие файлы не перезаписываются)
yukino new -i
```

Флаги подкоманды `new`:
- `--app` — создать исполняемое приложение (поведение по умолчанию).
- `--static` — создать статическую библиотеку (`output = "static"`).
- `--dynamic` — создать разделяемую библиотеку (`output = "shared"`).
- `--macro` — создать пакет процедурного макроса компилятора (`output = "macro"`).
- `--workspace` — создать многопакетный универсальный воркспейс (`yukispace.toml`).
- `-i` / `--init` — инициализировать проект в текущем каталоге вместо создания нового.

> [!NOTE]
> Для организации монорепозиториев и многопакетных проектов (сочетающих несколько библиотек и приложений) Yukino предоставляет механизм универсальных воркспейсов (`yukispace.toml`). Полное руководство по конфигурации воркспейсов, инлайн-пакетам и наследованию зависимостей вынесено в отдельный документ: [Воркспейсы и многопакетные проекты](15-workspaces.md).

### 1.2 Сборка: yukino build

Компилирует проект в соответствии с манифестом:

```sh
# Сборка по умолчанию (профиль debug)
yukino build

# Сборка с явным профилем (debug, release или произвольный кастомный)
yukino build debug

# Принудительная пересборка проекта и всех библиотек в обход кэша (-b / --rebuild, алиас rb)
# Перекомпилирует с нуля проект и все библиотеки (включая stdlib и зависимости [libs.runtime])
yukino build -b
yukino build --rebuild

# Принудительное обновление и перекачивание зависимостей (--refresh-deps, алиас rd)
yukino build --refresh-deps

# Кросс-компиляция под указанный целевой таргет
yukino build --target x86_64-unknown-linux-musl

# Сборка с последующим запуском (только для app-проектов)
yukino build -r

# Собственный архив рантайма или полный отказ от рантайма
yukino build --runtime path/to/libyukino_rt.a
yukino build --no-runtime

# Включение фич (через запятую или повтор флага -F)
yukino build -F network,ssl --no-default-features

# Включение абсолютно всех фич и опциональных зависимостей
yukino build --all-features

# Сборка конкретного пакета в воркспейсе (-p / --package)
yukino build -p core_lib

# Задание числа потоков компиляции
yukino build -j 8

# Задание числа блоков кодогенерации (CGU)
yukino build --cgunits 4

# Переопределение параметров профиля на лету (-o key=value)
yukino build -o opt_level=2 -o strip=false

# Отключение вывода предупреждений компилятора
yukino build --no-warns

# Отображение расширенной информации о сборке (профиль, таргет, потоки, фичи, инициализация компилятора)
yukino build --extra-info

# Отключение любого вывода компилятора в stdout (выводит только 0 при успехе или 1 при ошибке)
yukino build --no-out

# Отключение логов компиляции библиотек (stdlib и зависимостей, отображает только файлы основного проекта)
yukino build --no-lib-log

# Включение вывода предупреждений сторонних библиотек и stdlib (по умолчанию предупреждения библиотек всегда глушатся)
yukino build --lib-warns
```

#### Поддерживаемые платформы

Компилятор поддерживает следующие целевые платформы:

- `x86_64-unknown-linux-gnu`
- `x86_64-unknown-linux-musl`
- `aarch64-unknown-linux-gnu`
- `aarch64-unknown-linux-musl`
- `x86_64-pc-windows-gnu`
- `x86_64-pc-windows-msvc`
- `aarch64-linux-android`

Для вывода таблицы поддерживаемых платформ с параметрами архитектуры, ОС, libc и хост-таргета используется команда:

```sh
yukic targets
```

### 1.3 Запуск: yukino run

Компилирует приложение (если артефакт устарел) и запускает его:

```sh
# Запуск профиля debug (используется по умолчанию)
yukino run debug

# Запуск конкретного бинарного пакета из воркспейса (-p / --package)
yukino run -p cli_tool

# Запуск с передачей аргументов командной строки приложению
yukino run -- --port 8080 --host 0.0.0.0

# Запуск с активацией фич
yukino run -F debug_log,ssl
yukino run --all-features

# Запуск с переопределением конфигурации
yukino run -o opt_level=1 -- arg1

# Запуск с отключением предупреждений или расширенной информацией
yukino run --no-warns
yukino run --extra-info

# Принудительная пересборка проекта и библиотек перед запуском (-b / --rebuild, алиас rb)
yukino run -b
yukino run --rebuild

# Сборка без вывода в stdout (0/1) перед запуском
yukino run --no-out

# Сборка без логов компиляции библиотек перед запуском
yukino run --no-lib-log

# Отображение предупреждений сторонних библиотек при сборке перед запуском
yukino run --lib-warns
```

Все аргументы после разделителя `--` передаются непосредственно в запускаемый бинарник и доступны через вызов `args()`.

### 1.4 Тестирование: yukino test

Запускает тестовый раннер Yukino: `yukino` собирает тестовый бинарник из функций `#[test]` в `yuki-work/local/build/test/<triple>/<имя>/` и исполняет его.

```sh
# Запуск всех тестов проекта
yukino test

# Тестирование конкретного пакета воркспейса (-p / --package)
yukino test -p core_lib

# Запуск тестов со всеми фичами манифеста
yukino test --all-features

# Запуск тестов с конкретными фичами и отключением default
yukino test -F integration --no-default-features

# Запуск с фильтром по имени теста или сьюта
yukino test test_auth

# Точное совпадение имени теста
yukino test "math::test_add" --exact

# Отображение stdout/stderr тестов во время исполнения
yukino test --nocapture

# Запуск только пропущенных тестов (#[ignore])
yukino test --ignored

# Запуск всех тестов, включая пропущенные
yukino test --include-ignored

# Немедленная остановка после первого сбоя
yukino test --fail-fast

# Печать списка тестов без их запуска
yukino test --list

# Переопределение таймаута на тест (в миллисекундах)
yukino test --timeout 5000

# Число потоков параллельного выполнения тестов
yukino test -j 4

# Принудительная пересборка тестового бинарника (-b / --rebuild, алиас rb)
yukino test -b
yukino test --rebuild
```

Подробное руководство по тестированию, атрибутам `#[test]`, `#[should_panic]`, `#[ignore]`, `#[timeout_ms]` и организации тестов в директории `tests/` вынесено в отдельный документ: [16. Тестирование и тест-раннер](16-tests.md).

### 1.5 Очистка: yukino clean

Удаляет временные артефакты и скомпилированные объектные файлы:

```sh
# Очищает каталог yuki-work/local/ (объектные файлы, собранные бинарники)
yukino clean

# Полная очистка, включая удаление lock-файла yuki-work/common/yuki.lock (-a / --all)
yukino clean -a
```

### 1.6 Глобальная конфигурация: yukino config

Позволяет просматривать и модифицировать глобальные параметры `yukino`. Расположение файла конфигурации зависит от платформы: Linux — `$XDG_CONFIG_HOME/yukino-lang/config.json` (по умолчанию `~/.config/yukino-lang/config.json`), Windows — `%APPDATA%\yukino-lang\config.json`, macOS — `~/Library/Application Support/yukino-lang/config.json`. Путь можно переопределить переменной окружения `YUKINO_CONFIG_PATH`.

```sh
# Путь к глобальному файлу конфигурации
yukino config path

# Вывод всех сохраненных параметров
yukino config list

# Чтение и запись произвольного значения
yukino config get cthreads
yukino config set minibar true
yukino config set full-lib-log true

# Установка глобального числа потоков компиляции по умолчанию
yukino config cthreads 8
```

#### Параметры конфигурации

| Ключ | Тип | Описание |
|---|---|---|
| `cthreads` | `int` | Число параллельных потоков компиляции и кодогенерации (переопределяется флагом `-j / --threads`). |
| `minibar` | `bool` | Режим отображения интерактивной панели ядер при компиляции. |
| `noanim` | `bool` | Отключение анимации исчезновения панели компиляции (`true` — мгновенное стирание, `false` — анимация включена). |
| `full-lib-log` | `bool` | Подробный лог сборки библиотек (`true` — показывать компиляцию каждого файла и CGU, `false` — показывать только статус сборки библиотеки). |

#### Дефолты

- `cthreads`: `8`
- `minibar`: `false`
- `noanim`: `false`
- `full-lib-log`: `false`

Подробнее о параметре `full-lib-log`:
- При `full-lib-log = false` (по умолчанию) для зависимостей и стандартной библиотеки в консольный лог выводятся только строки `Compiling {библиотека} library` и `Compiled {библиотека} library`. Внутренние файлы и кодогенерационные юниты (CGU) библиотек не загромождают лог, при этом интерактивная панель ядер продолжает отображать их компиляцию в реальном времени.
- При `full-lib-log = true` выводятся полные логи компиляции всех промежуточных файлов и CGU библиотек.

Подробнее о режимах отображения панели ядер:
- При `minibar = false` (по умолчанию) используется многострочная панель с подробным отображением каждого активного ядра, автоматическим спуском неактивных ядер вниз и их схлопыванием в строку `○ [##] <N> more cores are currently idle`:
  ```text
  ● [01] codegen    cgu_0 (fn_main)  [ 3/10 |  30%]
  ● [02] optimizing cgu_1            [ 2/2  | 100%]
  ○ [##] 6 more cores are currently idle
  ```
- При `minibar = true` панель отображается в виде компактной одной строки со списком занятых ядер:
  ```text
  Processing 2/8 busy: [01] codegen cgu_0 · [02] opt cgu_1
  ```

### 1.7 Управление рантаймом: yukino runtime

Управляет предсобранными архивами рантайма, которые используются при линковке:

```sh
# Установка рантайма для таргета хоста (или конкретного таргета)
yukino runtime -i
yukino runtime -i x86_64-unknown-linux-musl

# Установка рантайма из локального архива (таргет обязателен)
yukino runtime -i x86_64-unknown-linux-gnu ./libyukino_rt.a

# Список, информация, удаление и переустановка рантаймов
yukino runtime -l
yukino runtime --info x86_64-unknown-linux-gnu
yukino runtime -r
yukino runtime --reinstall
```

Флаги `-i`/`--install`, `-r`/`--remove`, `-l`/`--list`, `--info` и `--reinstall` взаимоисключающие; вызов без флага завершается ошибкой.

## 2. Манифест yuki.toml

Манифест расположен в корне проекта: для приложений это `yuki.toml` (секция `[bin]`), для библиотек — `lib.toml` (секция `[lib]`). Манифест определяет настройки сборки, дерево зависимостей и параметры компиляции.

### 2.1 Секция [bin] (исполняемый файл)

Используется для бинарных приложений:

```toml
[bin]
name = "my_app"              # Имя исполняемого файла в release-режиме
namedbg = "my_app_debug"      # Имя исполняемого файла при сборке профиля debug
version = "0.1.0"            # Версия проекта
entry = "src/main.ykn"        # Главная точка входа
yukino = ["0.1.0", "+"]       # Поддерживаемый диапазон версий компилятора [min, max]
includes = ["stdlib"]        # Встроенные компоненты проекта (по умолчанию ["stdlib"])
```

Параметр `includes` управляет списком встроенных компонентов (builtins) компилятора в проекте:
- При генерации проекта (`yukino new`) в конец секции `[bin]` или `[lib]` автоматически добавляется `includes = ["stdlib"]`.
- Если параметр `includes` не указан в манифесте, проект по умолчанию расценивается как `includes = ["stdlib"]`.
- Если определенного компонента (например, `stdlib`) нет в массиве (например, `includes = []`), он не подключается: его модули недоступны (даже при использовании `load std`), а архивы не линкуются.
- Рантайм языка (`runtime`) присутствует и линкуется всегда независимо от `includes` (если не указан флаг `--no-runtime`).

### 2.2 Секция [lib] (библиотека)

Используется для библиотечных пакетов:

```toml
[lib]
name = "my_lib"
version = "0.1.0"
entry = "my_lib/lib.ykn"      # Точка входа библиотеки
yukino = ["0.1.0", "+"]
output = "static"             # Тип библиотеки: "static" (.a), "shared" (.so / .dll) или "macro" (процедурный макрос для хост-платформы); по умолчанию "static"
includes = ["stdlib"]        # Встроенные компоненты проекта (по умолчанию ["stdlib"])
```

### 2.3 Управление зависимостями: [libs.runtime] и [libs.build]

Yukino строго разделяет контексты выполнения и сборки:
- `[libs.runtime]` — рантайм-зависимости. Библиотеки компилируются под целевую платформу (`target`) и доступны только для кода основного приложения (из каталога `src/`).
- `[libs.build]` — сборочные зависимости. Все библиотеки из этого раздела компилируются под платформу хоста (на которой запущен компилятор) и попадают в область видимости предсборочного скрипта `build.ykn`. Вы можете загружать их через `load <имя>: ...` внутри `build.ykn`. При этом они не попадают в итоговый исполняемый файл приложения, если не требуются во время работы программы. Если зависимость является исполняемой утилитой кодогенерации (приложение с `main`), Yukino автоматически компилирует и запускает ее перед компиляцией основного кода.

Предпочтительным и компактным стилем описания зависимостей является таблица `[libs.runtime]` (или `[libs.build]`) с inline-таблицами для каждого пакета:

```toml
[libs.runtime]
# 1. Локальная зависимость (path)
local_math = { path = "../libs/local_math", features = ["simd"], default_features = false }

# 2. Git-репозиторий по тегу (tag)
json_parser = { git = "https://github.com/example/json-yukino", tag = "v1.2.0" }

# 3. Git-репозиторий по ветке (branch)
crypto_lib = { git = "https://github.com/example/crypto-yukino", branch = "main" }

# 4. Git-репозиторий по точному коммиту (commit)
exact_dep = { git = "https://github.com/example/exact-dep", commit = "d3b07384d113edec49eaa6238ad5ff00" }

# 5. Загрузка архива по URL с проверкой хэша (link, checksum)
zlib_wrapper = { link = "https://example.com/releases/zlib_wrapper-0.3.0.tar.zst", checksum = "blake3:5d0f8a1d4c3b5e6f7a8b9c0d1e2f3a4b5c6d7e8f9a0b1c2d3e4f5a6b7c8d9e0f1a2b" }
```

> [!TIP]
> Запись в виде отдельных секций (например, `[libs.runtime.local_math]`) также допустима по стандарту TOML, однако запись через единую секцию `[libs.runtime]` и inline-таблицы предпочтительна для удобства чтения.

Поддерживаемые параметры описания пакета (`DependencySpec`):
- `path`: относительный путь к каталогу локальной библиотеки (содержащему `yuki.toml`, `lib.toml` или `yukispace.toml`).
- `package`: имя конкретного пакета внутри воркспейса или каталога со множеством библиотек (поддерживаются взаимозаменяемые алиасы `sublib`, `subpath`, `lib`).
- `optional`: логический флаг (`optional = true`), делающий зависимость опциональной (подключается только при явной активации через фичу `dep:<name>`).
- `git`: URL удаленного Git-репозитория (`https://...` или `git@...`).
- `tag`: конкретный релизный тег Git.
- `branch`: ветка Git (автоматически отслеживается при `--refresh-deps`).
- `commit`: точный SHA хэш коммита.
- `link`: прямой URL скачиваемого архива (поддерживаются форматы `.tar.zst`, `.tar.gz`, `.tar.xz`, `.zip`, `.tar`, а также сокращения `.tgz` и `.txz`).
- `checksum`: контрольная сумма архива BLAKE3 в формате `blake3:<hex>` для верификации целостности.
- `features`: список фич зависимости (например, `["simd", "ssl"]`), передаваемых компилятору при сборке зависимости.
- `default_features`: управление стандартными фичами зависимости (`default_features = false` отключает секцию `default` зависимости).

### 2.4 Низкоуровневые C и системные библиотеки: [libs.static]

Секция `[libs.static]` управляет непосредственной передачей параметров линковщику:

```toml
[libs.static]
# Дополнительные прекомпилированные .o файлы
objects = ["src/native_glue.o"]

# Пути к статическим архивам .a
archives = ["libs/libcustom_c.a"]

# Каталоги поиска библиотек для флага -L
search_paths = ["libs/", "/usr/local/lib"]

# Системные библиотеки для флага -l (линкует -lm, -lpthread, -ldl)
system = ["m", "pthread", "dl"]
```

### 2.5 Таргет-специфичные зависимости: [targets.<triple>]

Позволяет переопределять зависимости и системные библиотеки в зависимости от целевой платформы (Target Triple):

```toml
# Настройки исключительно для Linux x86_64
[targets."x86_64-unknown-linux-gnu".libs.static]
system = ["pthread", "dl", "rt"]

# Настройки для Windows MSVC
[targets."x86_64-pc-windows-msvc".libs.static]
system = ["ws2_32", "user32", "advapi32"]
```

### 2.6 Профили компиляции: [config.<profile>]

Каждый профиль (например, `[config.release]`, `[config.debug]`) описывает параметры оптимизации. Профиль `release` по умолчанию использует `opt_level = 3`, `lto = true`, `strip = true`, `strip_unused = true` и `inline_statics = true`; любой другой профиль стартует от debug-значений (`opt_level = 0`, `debug_assertions = true`). Неуказанные поля берутся из этих значений по умолчанию.

На сборку в данный момент влияют только эти поля:

```toml
[config.release]
opt_level = 3                 # Уровень оптимизации: 0, 1, 2, 3, "s" (размер), "z" (агрессивный размер)
lto = true                    # Link-Time Optimization: false, true/"fat", "thin" (все включенные варианты передают один флаг --lto)
strip = true                  # Удаление отладочных символов из финального файла
strip_unused = true           # Активация Dead Code Elimination (DCE)
function_sections = true      # Размещение функций и статических данных в отдельных секциях (.text.<sym>, .rodata.<sym>) для эффективного удаления неиспользуемого кода линковщиком (--gc-sections)
codegen_units = 8             # Количество параллельных блоков кодогенерации (CGU)
```

Параметр `function_sections = true` генерируется по умолчанию в профиле `release` при создании проекта.

Приоритет разрешения числа кодогенерационных юнитов (`cgunits`):
1. Явный флаг командной строки `--cgunits <N>` (или `--codegen-units <N>`).
2. Поле `codegen_units` в конфигурации текущего профиля `[config.<профиль>]`.
3. Настройка `cthreads` в глобальном файле конфигурации `config.json`.
4. Количество ядер процессора (fallback).

Остальные поля ниже распознаются манифестом и могут переопределяться флагом `-o`, но пока не передаются компилятору `yukic` и не влияют на результат сборки:

```toml
inline_statics = true         # Встраивание static-констант прямо в места их использования (зарезервировано)
debug_assertions = false      # Включение внутренних assert-проверок компилятора (зарезервировано)
panic_strategy = "unwind"     # Стратегия паники: "unwind" (раскрутка стека) или "abort" (зарезервировано)
fast_math = false             # Разрешение агрессивных оптимизаций FP (зарезервировано)
cpu = "native"                # Модель процессора LLVM: "native", "generic", "x86-64-v3" и т.д. (зарезервировано)
features = ["+avx2", "+fma"]  # Специфичные инструкции процессора (зарезервировано)
reloc_model = "pic"           # Модель перемещения: "pic", "static" (зарезервировано)
code_model = "default"        # "default", "small", "kernel", "medium", "large" (зарезервировано)
emit = ["bin"]                # Выходные форматы: "bin", "obj", "asm", "llvm-ir" (зарезервировано)
```

### 2.7 Флаги сборки и условная компиляция: [features]

Определяет список фич, их взаимосвязи, форвардинг в зависимости и активацию опциональных зависимостей:

```toml
[libs.runtime.curl]
path = "../vendor/curl"
optional = true                 # Опциональная зависимость

[features]
default = ["std_io"]
std_io = []
network = []
ssl = ["network", "dep:curl"]   # Активирует фичу network и подключает опциональную зависимость curl
crypto_fast = ["crypto/simd"]  # Форвардинг фичи simd в зависимость crypto
crypto_opt = ["crypto?/avx"]   # Условный форвардинг: активирует avx у crypto, только если crypto активен
```

#### Правила синтаксиса фич:
- `dep:name` — явно активирует опциональную зависимость `name` (`optional = true`). Зависимость компилируется и линкуется только при включении данной фичи.
- `dep_name/feat` — безусловный форвардинг фичи: активирует фичу `feat` у подключаемой зависимости `dep_name`.
- `dep_name?/feat` — условный форвардинг: активирует фичу `feat` у зависимости `dep_name` только в том случае, если зависимость `dep_name` уже активирована через другую фичу.

#### Движок унификации фич (Feature Unification):
Если в графе зависимостей несколько библиотек зависят от одного и того же пакета с разными наборами фич (ромбовидная зависимость: библиотека `A` требует фичу `X`, а библиотека `B` требует фичу `Y`), пакетный менеджер Yukino производит автоматическое слияние требований (Unification). Зависимость собирается один раз с единым объединенным набором активированных фич `["X", "Y"]`.

#### Проверка фич в Yukino-коде:
В исходном коде проверка фич может выполняться несколькими способами:

1. **Унифицированный атрибут конфигурации `#[cfg(...)]` (рекомендуется):**
   ```yukino
   #[cfg(feature = "network")]
   fun init_sockets() {
       space
   }

   #[cfg(all(feature = "ssl", target_os = "linux"))]
   fun init_linux_ssl() {
       space
   }
   ```

2. **Макрос времени компиляции `cfg!(...)`:**
   Вычисляется на этапе синтаксического анализа в константный `true` или `false`:
   ```yukino
   if cfg!(feature = "network") {
       connect()
   }
   ```

3. **Исторический атрибут `#[feature = "..."]` и `#[!feature = "..."]`:**
   Сохраняется для обратной совместимости. Атрибут `#[!feature = ...]` работает как отрицание: элемент компилируется, когда фича выключена.

### 2.8 Секция тестов: [test]

Конфигурация встроенного тестового фреймворка:

```toml
[test]
threads = "auto"              # Число потоков ("auto" или фиксированное число, например 4)
timeout_ms = 10000            # Таймаут на выполнение одного теста в миллисекундах
capture_output = true         # Перехватывать stdout/stderr во время тестов
fail_fast = false             # Останавливать выполнение при первой упавшей проверке
tests_dir = "tests"           # Каталог с файлами интеграционных тестов
```

### 2.9 Пользовательские блоки кодогенерации: [customcgus]

Секция `[customcgus]` позволяет вручную нарезать проект или библиотеку на изолированные блоки кодогенерации (CGU). Это позволяет ускорить параллельную сборку и делает библиотеки модульными для компоновщика (линковщик компонует из статического архива `.a` только те `.o`, чьи символы реально используются):

```toml
[customcgus]
cgu_io = ["std/io.ykn", "std/platformio", "std/outf.ykn"]
cgu_fs = ["std/fs"]
cgu_strings = ["std/strings.ykn", "std/numf.ykn"]
cgu_math = ["std/math.ykn", "std/random.ykn"]
cgu_compress = ["std/compress.ykn"]
```

Правила работы:
- Если имя группы не начинается с `cgu_`, компилятор автоматически добавляет префикс `cgu_` (например, `io` становится `cgu_io`).
- Значения представляют собой списки подстрок или масок путей исходных файлов.
- Все элементы и функции, не подошедшие ни под один шаблон `[customcgus]`, компилятор автоматически распределяет по дополнительным CGU алгоритмом LPT-балансировки нагрузки.
- Секция `[customcgus]` не создается автоматически при выполнении `yukino new`, разработчик добавляет ее при необходимости точечной оптимизации модульности сборки.

## 3. Рабочий каталог yuki-work и блокировка yuki.lock

При первой сборке `yukino` автоматически создает локальное рабочее окружение:

```
my_app/
├── yuki.toml                 # Манифест проекта
├── src/
│   └── main.ykn
└── yuki-work/                # Рабочий каталог сборки
    ├── common/
    │   └── yuki.lock         # Файл фиксации точных версий, хэшей и коммитов
    └── local/                # Каталог сборки (целиком добавляется в .gitignore)
        ├── deps/             # Загруженные локальные копии пакетов
        │   ├── cache/        # Скачанные архивы тарболов (.tar.zst и др.)
        │   └── json_parser/  # Исходники распакованной зависимости
        ├── cache/            # Кэш CGU-объектников компилятора
        └── build/
            └── debug/        # Объектные файлы и бинарники профиля debug
                └── x86_64-unknown-linux-gnu/
                    └── my_app/
                        └── my_app_debug
```

В `.gitignore` автоматически добавляется только `yuki-work/local/`; каталог `yuki-work/common/` с файлом `yuki.lock` предназначен для коммита в репозиторий. На Windows к имени исполняемого файла добавляется расширение `.exe`.

### Файл фиксации yuki.lock

Файл `yuki-work/common/yuki.lock` генерируется автоматически (формат TOML) и фиксирует точное состояние сборки: целевой таргет, версию компилятора и имя профиля, а для каждого пакета:
- Название, версию и тип пакета (`app`, `static` и т.д.).
- Источник (`path+...`, `link+...` или `git+...`).
- Вычисленный хэш BLAKE3 (`checksum = "blake3:..."`): для скачанных архивов — хэш архива, для локальных исходников — контрольная сумма дерева исходников.
- Конкретный зафиксированный SHA коммита Git-зависимости (`commit = "..."`), если есть.
- Активированные фичи и список зависимостей (для корневого пакета — имена его runtime-зависимостей).

Благодаря `yuki.lock`, сборка является детерминированной и воспроизводимой на любых машинах. Для обновления зафиксированных версий используется флаг `yukino build --refresh-deps`.

## 4. Скрипт предсборки build.ykn

Если в корне проекта находится файл `build.ykn`, `yukino` автоматически компилирует и исполняет его **перед** сборкой основного приложения.

Скрипт `build.ykn` пишется на чистом Yukino и используется для:
1. Вызова системных утилит (компиляция C-кода через GCC/Clang, генерация кода).
2. Динамической передачи флагов линковщику через стандартный вывод (`stdout`).
3. Чтения параметров окружения и целевой архитектуры сборки.

### 4.1 Переменные окружения и макросы

При запуске скрипта `build.ykn` (и утилит из `[libs.build]`) ему передаются переменные окружения:

| Переменная | Описание |
| :--- | :--- |
| `YUKINO_PROJECT_DIR` | Корень проекта (каталог с `yuki.toml` / `lib.toml`) |
| `YUKINO_OUT_DIR` | Каталог артефактов текущей сборки: `yuki-work/local/build/<profile>/<triple>/<имя>` |
| `YUKINO_TARGET_TRIPLE` | Целевой таргет сборки (например, `x86_64-unknown-linux-gnu`) |
| `YUKINO_TARGET_OS` | ОС целевого таргета: `linux`, `windows` или `android` |
| `YUKINO_TARGET_ARCH` | Архитектура целевого таргета: `x86_64` или `aarch64` |
| `YUKINO_PROFILE` | Имя активного профиля (дополнительно, только для утилит из `[libs.build]`) |

Скрипт компилируется под таргет хоста. В нем доступна стандартная библиотека (подключается обычным `load std.io: ...`, если код ее использует), сборочные библиотеки из секции `[libs.build]` манифеста `yuki.toml` (подключаются через `load <имя>: ...`), а также встроенные макросы:

- `get_target!()` — целевой таргет сборки (например, `"x86_64-unknown-linux-gnu"`).
- `get_profileconfig!()` — имя активного профиля сборки (`"release"`, `"debug"` и т.д.).
- `get_features!()` — массив активированных фич сборки (`string[]`).
- `hostenv!("VAR_NAME")` — значение переменной окружения хоста на этапе сборки.
- `yukienv!("key")` — чтение параметров манифеста (например, `"bin.name"` или `"config.release.opt_level"`).

### 4.2 Директивы stdout

Вывод определенных префиксов в `stdout` из `build.ykn` перехватывается сборочным процессом `yukino`:

| Директива stdout | Описание |
| :--- | :--- |
| `yuki:link-archive=PATH` | Добавляет статический архив (`.a`) или объектный файл к линковке |
| `yuki:link-system=LIB` | Передает системную библиотеку линковщику (аналог `-l LIB`) |
| `yuki:warning=TEXT` | Выводит предупреждение в журнал сборки |

Другие директивы (`cfg`, `rerun-if-changed` и т.п.) на данный момент не поддерживаются.

### 4.3 Пример build.ykn

Пример `build.ykn`, передающего линковщику заранее собранный нативный архив и системную библиотеку:

```yukino
load std.io: print

fun main() {
    // Получение целевого таргета
    set target_arch = get_target!()
    
    // Передача статического архива (например, собранного C-кода)
    print("yuki:link-archive=native_libs/libwrapper.a\n")
    
    // Передача системной библиотеки
    print("yuki:link-system=m\n")
    
    // Предупреждение в журнале сборки
    print("yuki:warning=native wrapper linked\n")
}
```
