# Обработка ошибок и исключения (sus, catch, finally, panic)

В языке Yukino принята строгая, предсказуемая и явная модель обработки ошибок. Она разделяет логическое отсутствие данных и непредвиденные сбои времени выполнения, обеспечивая нулевые накладные расходы на проверку в счастливом пути («zero-cost exceptions») и полную типизацию контекста ошибок при раскрутке стека.

## 1. Философия и стратегия обработки ошибок

В Yukino строго разграничиваются две ситуации:

1. **Логическое отсутствие ожидаемого значения при штатной работе**:
   Если данные не найдены в словаре, файл пуст при неблокирующем чтении или не удалось распарсить необязательный параметр — функция возвращает `null` (опциональный тип `T?`).
   Никаких фиктивных значений (вроде пустой строки вместо ошибки или `-1` в виде валидного идентификатора) не допускается.

2. **Ошибки времени выполнения и исключительные ситуации**:
   Если операция не может завершиться успешно (деление на ноль, обрыв сетевого соединения, отсутствие обязательного дескриптора, повреждение формата данных) — генерируется исключение через `panic`.
   Исключение всегда передается как экземпляр структуры. Передача сырых строк или чисел запрещена компилятором.
   Код обязан быть готов перехватить такое исключение через блок `sus ... catch`.

Если функция по своей семантике не возвращает полезных данных (например, закрытие дескриптора или синхронизация мьютекса), она должна возвращать индикатор результата (например, `bool`), чтобы вызывающая сторона могла убедиться в завершении операции.

В конфигурации проекта `yuki.toml` поведение при панике задается стратегией `panic_strategy` в секции профиля `[config.<profile>]` (например, `[config.debug]` или `[config.release]`):

```toml
[config.debug]
panic_strategy = "unwind" # По умолчанию для debug: раскрутка стека

[config.release]
panic_strategy = "abort"  # Опционально для release: мгновенный аборт
```

### Сравнение стратегий: unwind против abort

Компилятор Yukino поддерживает две стратегии обработки паники:

| Характеристика | `unwind` (раскрутка стека) | `abort` (мгновенный сброс) |
| :--- | :--- | :--- |
| **Поведение при `panic`** | Раскрутка стека через DWARF landing pads | Немедленное завершение процесса через `SIGABRT` (`abort()`) |
| **Блоки `sus ... catch`** | Полностью работают, ошибки перехватываются | Не перехватывают: при первой же панике процесс аварийно завершается |
| **Выполнение `defer` и `finally`** | Гарантированно выполняются при раскрутке | При панике не выполняются (выполняются только при штатном выходе) |
| **Таблицы исключений (LSDA)** | Генерируются в бинарнике | Не генерируются (нулевой оверхед по размеру таблиц) |
| **Размер исполняемого файла** | Выше из-за landing pads и метаданных исключений | Минимальный (нет DWARF landing pads, меньше размер машинного кода) |
| **Оптимизации компилятора** | Вызовы функций могут быть landing pad инвокациями | Максимальные (`-O3`, инлайнинг без проверок раскрутки) |

#### Где и какую стратегию использовать

* **Используйте `panic_strategy = "unwind"`:**
  * **Сетевые и серверные приложения:** обработка HTTP/RPC запросов, веб-сервисы, фоновые воркеры, где сбой обработки одного клиентского запроса не должен приводить к падению всего сервиса.
  * **Парсеры и трансляторы:** разбор недоверенных внешних данных (JSON, конфигов, протоколов), где при ошибке формата данных необходимо поймать панику через `catch` и вернуть понятную ошибку вызывающему коду.
  * **Управление ресурсами:** критические сценарии, где отложенные действия `defer` (закрытие дескрипторов, сетевых сокетов, снятие локов) обязаны гарантированно выполниться даже в случае аварийной остановки подпрограммы.

* **Используйте `panic_strategy = "abort"`:**
  * **CLI-утилиты и консольные скрипты:** одноразовые утилиты и сценарии пакетной обработки, где любая непредвиденная ошибка должна мгновенно останавливать выполнение команды с ненулевым статусом (принцип Fail-Fast).
  * **Микросервисы архитектуры Crash-Only:** облачные контейнеры и воркеры, которые перезапускаются оркестратором (Kubernetes / systemd) при падении.
  * **Embedded и экстремальная оптимизация по размеру:** сценарии с жесткими ограничениями на объем памяти и размер исполняемого файла, где критически важно исключить из бинарника landing pads и таблицы DWARF.

## 2. Конструкция sus, catch, finally

Для безопасного выполнения рискованного кода используется блок `sus`:

```yukino
sus {
    // Защищенный блок: при возникновении panic управление
    // передается в соответствующий блок catch
    do_risky_io()
} catch {
    // Обработка ошибки
} finally {
    // Блок, выполняемый всегда (при успешном завершении sus или после catch)
    cleanup_resources()
}
```

### Правила выполнения

- Если блок `sus` завершился успешно, блок `catch` пропускается, и выполняется блок `finally` (если он объявлен).
- Если внутри `sus` сработал `panic`, выполнение прерывается, последовательно выполняются все отложенные инструкции `defer` внутри защищенной области, после чего управление передается в блок `catch`, тип которого совпал с типом исключения (или в универсальный `catch` без указания типа).
- Блок `finally` выполняется гарантированно даже при перехвате исключения.
- Если ни один блок `catch` не совпал по типу (и универсального `catch` нет), исключение повторно пробрасывается выше по стеку, а блок `finally` данного `sus` не выполняется.

## 3. Переменная errkind

Внутри любого блока `catch` компилятор автоматически предоставляет строковую переменную `errkind: string`.

| Переменная | Тип | Описание |
| :--- | :--- | :--- |
| `errkind` | `string` | Имя типа структуры, вызвавшей панику (например, `"JsonError"`, `"MathError"` или `"Panic"` для системных аварийных завершений) |

Переменная `errkind` доступна всегда: как в универсальном блоке `catch`, так и в типизированных `catch Struct` и `catch TempName: Struct`. Она позволяет однозначно определить источник ошибки даже в универсальном обработчике.

## 4. Формы перехвата catch

Yukino поддерживает три взаимодополняющие формы перехвата ошибок в блоке `catch`:

1. **Типизированный перехват с именем структуры (`catch TempName: Struct`)**:
   Перехватывает только ошибки типа `Struct` и объявляет в теле блока локальную переменную `TempName` с типом `Struct`.
   Вся структура ошибки полностью передается в область видимости: доступны абсолютно любые ее поля (`TempName.field`) с их исходными значениями времени выполнения.

2. **Типизированный перехват без переменной (`catch Struct`)**:
   Перехватывает только исключения типа `Struct`, однако в область видимости блока `catch` локальная переменная не помещается. Используется, когда достаточно знать тип произошедшей ошибки, а доступ к ее внутренним полям не требуется.

3. **Универсальный перехватчик (`catch`)**:
   Перехватывает любые исключения, для которых не сработали предшествующие блоки `catch`. В область видимости переменная структуры не экспортируется, но доступна переменная `errkind: string`.

> [!IMPORTANT]
> **Импорт структуры ошибки для типизированного перехвата:**  
> Чтобы структура стала доступна в блоке `catch` через псевдоним (`catch e: JsonError`) и можно было безопасно обращаться к её полям (`e.line`), её тип обязан находиться в области видимости текущего файла. Если структура ошибки объявлена во внешнем модуле или сторонней библиотеке, её обязательно нужно импортировать через `load`. Иначе компилятор не сможет сопоставить поля структуры и выдаст ошибку:
>
> ```yukino
> load json: parse_data, JsonError
>
> sus {
>     parse_data(raw_payload)
> } catch e: JsonError {
>     // Поля e.line и e.message доступны, так как JsonError импортирован
>     set x = e.line
> } catch {
>     // Если тип не импортирован, узнать имя структуры можно только через errkind
>     println("Ошибка: " + errkind)
> }
> ```

### Пример: комплексная обработка с JsonError

Рассмотрим структуру ошибки парсинга JSON:

```yukino
public struct JsonError {
    message: string
    line: int64
    column: int64
    offset: int64
}
```

Пример безопасного парсинга и дифференцированного перехвата:

```yukino
load std.io: println

public struct JsonError {
    message: string
    line: int64
    column: int64
    offset: int64
}

public struct NetworkError {
    code: int32
    endpoint: string
}

fun parse_payload(raw: string) {
    if raw.len() == 0 {
        panic(JsonError {
            message: "unexpected end of file",
            line: 1,
            column: 1,
            offset: 0,
        })
    }
}

fun main() {
    sus {
        parse_payload("")
    } catch err: JsonError {
        // Доступна переменная err со всеми полями JsonError:
        println("Ошибка парсинга JSON: " + err.message)
        println("Строка:  " + cast(err.line, "string"))
        println("Колонка: " + cast(err.column, "string"))
        println("Смещение: " + cast(err.offset, "string"))
        println("Тип ошибки: " + errkind) // "JsonError"
    } catch NetworkError {
        // Перехватывает NetworkError без внесения переменной в область видимости
        println("Сетевой сбой при загрузке документа (тип: " + errkind + ")")
    } catch {
        // Универсальный обработчик для всех остальных исключений
        println("Неизвестная ошибка: " + errkind)
    } finally {
        println("Завершение разбора")
    }
}
```

## 5. Генерация исключений: интринсик panic

Для инициирования аварийной остановки или раскрутки стека используется интринсик компилятора `panic`:

```yukino
panic(payload: S) -> never
```

- **Параметр:** `payload` — экземпляр структуры ошибки (обязан быть типом `struct`).
- **Возвращаемый тип:** `never` — управление никогда не возвращается в следующую инструкцию.

Попытка передать в `panic` значение базового типа (строку, число, массив) или вызвать `panic()` без параметров приводит к ошибке типизации на этапе компиляции:

```yukino
// Ошибка компиляции: panic requires an argument of struct type
panic("something went wrong")
```

## 6. Проектирование структур ошибок: Best Practices и Anti-patterns

В Yukino приняты строгие стандарты оформления кода ошибок.

### 6.1 Как создавать структуры ошибок (Best Practices)

1. **Всегда используйте типизированные структуры**: создавайте для каждого домена собственную структуру ошибки с понятным именем (`JsonError`, `MathError`, `IoError`, `ThreadError`).
2. **Определяйте информативные поля**: добавляйте все необходимые для диагностики поля: текст (`message: string`), коды (`code: int32`), координаты (`line: int64`, `column: int64`), пути файлов или имена хостов.
3. **Используйте точные типы**: избегайте нетипизированных полей, задавайте точные целочисленные и строковые типы.

```yukino
// Пример качественной структуры ошибки
struct FileNotFoundError {
    message: string
    code: int32
    path: string
}

if !exists(filename) {
    panic(FileNotFoundError {
        message: "file does not exist",
        code: 404,
        path: filename,
    })
}
```

### 6.2 Чего делать НЕЛЬЗЯ (Anti-patterns)

#### Антипаттерн 1: Замалчивание ошибок и поддельные фоллбеки
```yukino
// ПЛОХО: маскировка критического сбоя возвратом фейкового нуля
fun read_config_int(key: string) -> int32 {
    if !has_key(key) {
        return 0 // Вызывающий код не поймет, ключ равен 0 или его нет
    }
    // ...
}

// ХОРОШО: возврат опционального типа T?
fun read_config_int(key: string) -> int32? {
    if !has_key(key) {
        return null
    }
    // ...
}
```

#### Антипаттерн 2: Пустые блоки перехвата
```yukino
// ПЛОХО: исключение проглочено без диагностической пользы
sus {
    critical_migration()
} catch {
    // пусто
}
```

## 7. Взаимодействие с defer и регионами памяти

Модель исключений Yukino полностью интегрирована с системой автоматического управления памятью и отложенными действиями:

1. **LIFO-вызов `defer` при раскрутке**:
   Если внутри защищенного блока были объявлены операторы `defer`, при срабатывании `panic` они будут выполнены в обратном порядке (LIFO) до того, как управление перейдет в `catch`.

2. **Очистка региональной памяти (`region`)**:
   Память, выделенная внутри блоков `region` на стековых страницах фрейма, при раскрутке стека освобождается без утечек указателей.

```yukino
load std.io: println

struct IoError {
    message: string
    code: int32
}

fun example() {
    sus {
        set handle = open_resource()
        defer close_resource(handle) // Гарантированно выполнится даже при panic ниже

        panic(IoError {
            message: "read failure",
            code: 5,
        })
    } catch err: IoError {
        println("Ресурс уже безопасно закрыт, ошибка: " + err.message)
    }
}
```
